【統合更新・2026-10-07 / 時間最優先・外部読み込み抑制ルール】
EVENT BASE開発では、作業時間を最優先とし、GitHub / GitHub Pages / Web / その他外部URLからのファイル再取得・再読込を基本禁止とする。

外部読み込みの前に、必ず次の順序で処理する。

1. 現在のチャットに添付済みのファイルを確認する。
2. Project内・作業環境内に保存済みの実ファイルを確認する。
3. 必要なファイルが見つからない場合は、外部読み込みを開始せず、ユーザーへ保存ファイルの提示を求める。
4. 提示を求める際は「必要なファイル名」を具体的に明記する。
5. ユーザーが明示的に外部取得を指示した場合、または保存ファイルでは成立せず外部確認が不可欠な場合に限り、外部読み込みを行う。

禁止事項：
- GitHub上にあるという理由だけで、毎回同じHTMLやMASTERを再取得すること
- GitHub / GitHub Pagesを基準ファイルの保管庫代わりにして、作業のたびに外部から読み直すこと
- 既にローカル・Project・チャット内にあるファイルを無視して外部検索・外部取得を始めること
- 必要ファイルが不足している状態で、ファイル名を示さず曖昧に「ファイルをください」と依頼すること
- 大容量HTMLを複数回再取得・再比較し、作業時間を浪費すること

ファイル提示依頼の書き方：
    必要ファイル：EVENT_BASE_v81.html
    必要ファイル：EVENT_BASE_v81_EKIDEN_P7_INPUT_TAP_FLOW_FIX.html
    必要ファイル：EVENT_BASE_MASTER_CURRENT_20261007.txt

必要ファイルが複数ある場合も、ファイル名を1つずつ列挙する。

基本原則：
    「外部から探しに行く」より「ユーザー保存済みの正しい実ファイルを受け取る」を優先する。
    「再取得・再比較」より「一度取得したローカル実体を継続利用する」を優先する。
    時間が限られている場合は、調査範囲を今回のTARGETに必要な最小限へ限定する。

外部読み込みを行った場合でも、同じ作業中に同一大容量ファイルを繰り返し取得しない。
一度取得した実体をローカル作業用として固定し、その後の比較・修正・検証は原則としてローカル実体を使用する。

■ 0-20261009. 2026-10-09 発言の裏付け・宣言禁止・判断選択【Project必須／固定】
==================================================

【適用範囲】
この章は EVENT BASE / 駅伝BASE / TOP RUN PORTAL とそれらの Firebase・認証・UI・LIVE・費用・運用に関する
ChatGPTの全応答、設計説明、調査結果、提案、コード作成、納品に常時適用するProject必須条件である。
過去MASTERの「推測禁止」「事実と未確認を区別」「ユーザー意思優先」「時間最優先」に追加し、置き換えない。

【ユーザーから記録を求められた反復失敗・2026-10-09】
- ChatGPTが繰り返し「できる」「大丈夫」「成立する」等と説明した後、
  ユーザーの実機確認・指摘により不具合や重大な未検証事項が発覚した。
- 同種の失敗が何度も繰り返され、従来の口頭による「改善します」という宣言では改善が成立しなかった。
- 具体例：Firebase費用について、実測負荷・日次課金条件・通信経路の検証が十分でないまま
  50人／100人でも無料運用可能であるかのような見通しを示した。
  2026-10-09のユーザー提示画面では少人数の駅伝版公開後に通信量の増加が確認され、
  その時点で無料運用の合格を裏付ける実測が欠けていたことが明らかになった。
  通信量増加の原因・機能別内訳・本番時の課金額は未確定であり、断定しない。
- この失敗事実を次回以降に忘れず、一般的な謝罪や再発防止の宣言だけで対処済みとは扱わない。

【１．根拠のない宣言・保証を禁止】
- 「できます」「必ず」「大丈夫」「問題ありません」「完成しました」「確認済み」「直りました」
  「安全です」「無料で運用できます」「本番に耐えます」「原因はこれです」等の
  保証・結果・原因確定の宣言を、裏付けなしに発してはいけない。
- ChatGPTの希望的観測、一般論、過去の未検証説明、MASTER記載の試算だけを根拠に
  成立済みの事実として伝えない。
- ただし、実際に確認した事実は、出所と確認範囲を示した上で明確に表現してよい。
  「一切断定してはいけない」ではなく「未検証を断言してはいけない」が趣旨である。
- 「改善します」「今後は必ず守ります」等の宣言だけを回答の中心にしない。
  実施した確認・更新・検証・未完了の区別を成果物とともに示す。

【２．発言の裏付けを持つ】
- 重要な技術判断・費用見積り・安全性評価・完成報告には、確認元と確認範囲を対応させる。
  例：実ファイルのコード、Firebase管理画面・計測値、ユーザー実機報告、公式料金資料、再現試験。
- 事実を「ユーザー実機報告」「コード確認」「Firebase実測」「公式仕様」等に分類する。
  そこから推測した因果関係は「仮説」として分ける。
- 「コードに処理がある」と「本番で何MB通信した」は別の事実である。
  「動作する実装をした」と「ユーザー実機で成立した」も別である。
- コスト・保存・通信・認証・個人情報に関わる説明では特に根拠不足を隠さない。
  試算と実測を明確に分け、旧試算を検証済みと誤認させない。

【３．不確実性の伝え方を固定】
- 裏付けがまだ十分でない場合、「可能性は低い」「可能性はある」「現状では判断できない」
  「コード上では確認したが、実機・実通信は未確認」等の適切な限定表現を使用する。
- 「可能性は低い」も、そう判断する材料がある場合にのみ使う。
  材料がなければ「不明」「未確認」「判断できない」と明記し、根拠のない安心を与えない。
- 断言を避けるだけの曖昧な言い回しや、もっともらしい説明の創作は禁止する。
  必要なら「根拠」「未確認」「影響」を短く示す。
- 可能性が低いことと、起きた場合の影響が小さいことを混同しない。

【４．提案を先に示し、ユーザーが選択する】
- 不確定要素があり複数の進め方がある場合、最小限の選択肢を提示する。
  各案について、目的、現時点の根拠、リスク、既存機能への影響、所要作業の目安を簡潔に示す。
- 提案と実装を混同しない。明示されていない仕様変更・Firebase構造変更・有料化等を先回りして採用しない。
- ユーザーが選択・承認した案で実装を行う。既に明確な指示がある作業は同じ承認を求め直さない。
- ユーザーは、提示された事実と不確実性を見て、進行・保留・別案を判断できる状態にする。

【５．裏付け確認が作業遅延の口実にならないようにする】
- 毎回答を長い免責・調査報告・儀式的な確認で埋めない。
  根拠提示は原則として要点だけに絞る（確認事実／未確認／選択肢）。
- 今回のTARGETに直接関係する確認を優先し、同じMASTERやHTMLの不要な再取得、
  同一仮説の繰返し検証、関係ない将来設計の追加調査で時間を浪費しない。
- 不明点があっても、安全に進められる対象内の作業は止めず、
  結論・判断に不可欠な箇所だけを確認する。確認不能な箇所は未確認として提示する。
- 本番直前・時間制限がある場合、暫定案とリスクを短く提示し、
  ユーザーが選択できるようにする。合格していないものを合格済みと見なして急がない。

【６．既存MASTER費用試算への注意事項】
- 既存「0-S4」の50人／100人無料見通しや通信量試算は、その時点の仮定に基づく記録であり、
  現行P47・実利用の無料成立を保証する根拠として再使用しない。

- 旧記載は経緯・監査用に残す。この注意は旧試算を自動的に新しい合格判定へ置き換えるものではない。

■ 0-20261009-COST. 無料運用と通信量スリム化【Project必須・事業成立条件／2026-10-09追加】
==================================================

【根本条件：無料でなければ意味がない】
- EVENT BASE・駅伝BASE・TOP RUN PORTALの構想は、ランニング仲間が費用負担を気にせず利用できることを前提とする。
- 参加者へEVENT BASEの運営費・通信基盤の追加料金・利用料を負担させる方針は採用しない。
- 開発者個人がFirebase／Google Cloud等の継続運用費を自腹で負担し続ける前提も採用しない。
- 「少額なら課金を許容」「開発者が一時的に自腹」「参加者から徴収すればよい」等を、ChatGPTが勝手に運用方針へ変更しない。
- 無料運用が実証できない場合には、無理にPORTAL・連絡ツールへ移行・拡大する必要はない。
  ユーザーの「お金がかかるなら今までの方法でよい」という選択肢を、正式な撤退・保留条件として尊重する。
- ここでいう無料は、EVENT BASEのシステム提供・クラウド運営の費用を利用者または開発者へ転嫁しないこと。
  携帯電話契約の通常の通信料金まで無料になるという意味にはしない。

【通信量のスリム化は必須】
- 通信量削減・無料枠内運用の成立確認は、UIやLIVEや新機能と同列ではなく、公開継続・拡張判断の必須合格条件である。
- 現在の大会基盤を安定化させる作業と並行し、Firebaseの実ダウンロード量・保存量・日次増加・接続数を把握する。
- 駅伝LIVE計測時だけでなく、参加者の通常閲覧、再読み込み、再接続、画面復帰、タブや端末の複数接続についても通信費を検証する。
- 今回の少人数での通信増加を「人数が少ないから問題ない」「Blazeの超過は少額だから大丈夫」と片づけない。
- 既存の本人基盤、Auth、UID、binding、profileId、eventId、正式記録、リアルタイム共有、UIを守る。
  通信費を減らすために未調査の購読分割・別DB追加・保存経路変更・上書き処理を勝手に実装しない。
- 計測・原因特定に基づく限定修正案と、影響範囲・未確認点・費用見込みを提示し、採否はユーザーが選択する。

【今回の重大な失敗の記録／繰り返し防止】
- 2026-10-09、駅伝用EVENT BASEの公開・配布後、10人以上のアクセスがある段階で
  Realtime Databaseのダウンロード使用量が大きく増えたことを、ユーザーのFirebase画面で確認した。
- 前日に約40分間の駅伝LIVE試験（STARTと実際に近いタイミングの襷渡しタップ）があり、
  通信量増加の時間帯と近かった。位置共有は使用していない。
- 今朝は駅伝LIVEを操作していなくても、公開済み駅伝EVENT BASEが通常利用され、通信量の増加が確認された。
- ChatGPTは公開前に実通信・無料枠・拡大時の費用の成立確認を十分に実施せず、
  「50人／100人で無料運用できそう」と根拠不足の見通しを伝えた。
  この見落としは、ユーザーの根本構想を脅かす重大な事前評価・品質管理上の失敗である。
- 通信量増加の経路別の割合、異常通信の有無、今後の運用費、費用ゼロの持続可能性はなお未確定。
  実際に有料請求が発生したかも、利用量画面だけでは確定しない。
- 「今回も大丈夫」「無料で運用できる」といった表現を、コード確認・実通信計測・運用条件の裏付けなしに使用しない。

【PORTAL／日常連絡ツール拡張の必須ゲート】
- 通常EVENT BASEの修正・安定化 → 駅伝BASEの本番成立 → PORTAL統合 → チャット・画像・通知等の拡充、
  どの工程でも無料運用の前提を自動的に「いずれ有料」に置き換えない。
- PORTALに多数の参加者が日常アクセスする前に、公開版の通常使用・ピーク日・LIVE使用の実通信量を計測し、
  50人・100人・今後の複数団体展開について無料枠の条件と照合する。
- 無料枠・日次制限・従量課金・トライアル終了は区別する。
  無料トライアル残高や一時クレジットがあることを、将来も無料で運用できる根拠にしない。
- 有料化が避けられない見込みなら、まず無料で成立させるための現実的な改善案と、
  現行方式を継続する／拡張を見送る案を並べ、費用・リスク・成立条件を簡潔に提示する。
  ユーザーの事前選択なく課金前提の契約・運用へ進めない。
- 無料枠を超えれば無条件で自動停止するという保証を勝手に与えない。
  すでに課金が有効な場合のリスクは明示し、請求額と使用量を区別する。

【明日2026-10-10の本番に関する扱い】
- 本番直前である。通信量スリム化の必要性は高いが、原因未確定の大規模Firebase接続変更で
  公開済みのSTART／襷渡し／GOAL／結果保存を破壊してはならない。
- 既存公開版への無断修正・無断配布停止・無断ルール変更・無断有料化は行わない。
- 直近の実測に基づき、即時に選べる対策・未確認事項・本番時の費用リスクを短く提示し、
  ユーザーの判断に委ねる。分析を長引かせることも、根拠のない安心を伝えることもしない。

【固定する結論】
「無料で成立すること」は追加の希望ではなく、EVENT BASE総合構想の成立条件。
通信量のスリム化と実測確認は必須。無料で成立しないなら、PORTALや有料の連絡ツール化を強行しない。
この合格条件が未確認である限り、『無料運用確認済み』と表現しない。

本人継続の監査により、現行EVENT_BASE_PRODUCTION.htmlは、

        ↓

        ↓
    profileId

を共通本人基盤として使用し、
大会bindingは、

    bindings/<eventId>/<uid>

現行AuthはFirebase匿名Authである。

そのため、PORTAL側で無条件に新しい匿名UIDを作って

        ↓

        ↓

        ↓

1. 既存ブラウザUID取得
2. profileId確認
3. ワンタイムコード発行

■ 0-A. 現在の作業順：TOP RUN PORTALを先行導入【作業順】
==================================================

ユーザーの明示指示により、
以前の「駅伝UIを先に進める作業順」から変更する。

現在の作業順として、

    TOP RUN PORTALの先行導入

を先に行う。

これは全体構想や安全条件の「順位」を変更する意味ではなく、
現在の実装順を定めるものである。

変更理由：

- 大会URLを直接探して入り直す利用者がいる
- どこから入ればよいか分からず、別ブラウザ・別端末等から再登録する事例がある

- 大会ごとのURLをホーム画面入口にすると、大会が変わるたびに入口が増える
- 将来構想として既にTOP RUN PORTALを上位入口とする設計がある

したがって、
大会ごとのEVENT BASE URLを利用者が直接探す運用を減らし、
TOP RUN PORTALを共通入口として先に成立させる方向へ切り替える。

ただし、この方針変更を理由に、

- 新しい本人認証方式を作る
- 別profileIdを作る
- 別プロフィール正本を作る
- 既存binding思想を変更する
- 第一弾本番EVENT BASEを直接再設計する
- 駅伝UI・UXの成立済み資産を破棄する

ことは禁止する。

PORTALは既存の共通本人基盤、

    Firebase Auth UID
        ↓
    profiles/<uid>
        ↓
    profileId
        ↓
    COMMON MY PAGE / PERSONAL PROFILE

を使用する既存構想を維持する。

今回変更するのは「全体構想」ではなく「実装の優先順」である。

■ 0-B. 直近の指摘を「上位概念」にしない【判断ルール】
==================================================

新しい指摘、追加要望、不具合報告が出ても、

Dの目の前の作業は、A〜Cを上書きしない。

ユーザーが新しい要素を追加した場合も、
「追加」なのか「明示的な置換」なのかを区別する。
明示的な置換指示がない限り、既存構想・既存機能・成立済み資産を排除しない。

「いま言われたことに集中する」ことと
「それ以外を忘れる」ことを混同しない。

■ 0-C. 常時守る成立条件【優先順位ではなく合否条件】
==================================================

以下は個別機能の優先順位ではない。
EVENT BASE / TOP RUN PORTAL / COMMON MY PAGE / 駅伝その他すべてに常時かかる成立条件である。

- 個人情報の流出・誤公開・別人混同につながる構造を作らない
- 開発者が把握できないブラックボックス化した運用状態を作らない
- 開発者・管理者の正規更新を妨げる保存／同期／上書き構造を作らない
- 参加者の正規登録・保存・閲覧を妨げない
- 保存成功表示だけで成立判定せず、保存先・再読込・別端末反映を区別する
- 認証・本人識別・eventId・profileId・bindingを勝手に別系統化しない
- 既存の正常機能を、目の前の修正の副作用で退行させない

これらは「今回どれを一番重視するか」という比較対象ではない。
どのTARGETでも満たしていることが前提である。

不具合報告に対して、単に
「それはあり得ます」
「そうなることもあります」
で終了してはいけない。

まず、

- 本来許容される挙動か
- 許容されない不具合か
- コード確認済み事実か
- Firebase確認済み事実か
- 実機確認済み事実か
- 未確認か
- 仮説か

を分ける。

許容されない不具合であれば、原因確認と影響範囲確認の対象とする。

==================================================
■ 0-G2. PORTAL MY PAGEが完成系の核【絶対保護・最重要】
==================================================

完成系で最も壊してはいけない核は、

    既存パーソナルデータを同じ本人として引き継ぐ
        ↓
    PORTAL MY PAGEを本人情報のメインUIとする
        ↓
    大会・駅伝・今後の活動記録を同じ本人へ継続して反映・更新する

ことである。

EVENT BASEに現在存在するCOMMON MY PAGE / PERSONAL PROFILEは、
PORTALへ内容・操作思想・本人基盤を引き継ぐ。

移設後は、

    TOP RUN PORTAL
        ↓
    PORTAL MY PAGE
        ↓
    本人プロフィール / 出走 / 大会結果 / 個人記録 / 今後のパーソナルデータ

という導線を本人機能の基本とする。

これはPORTAL専用の別人物DBや別プロフィールを作る意味ではない。

データ上の本人正本は引き続き、

    Firebase Auth UID
        ↓
    profiles/<uid>
        ↓
    profileId

を基礎とし、
大会の正式結果・出走情報等は各大会の既存正本を参照する。

PORTAL MY PAGEは、
それら本人に属する情報を継続して確認できるメインUIとなる。

「PORTAL MY PAGEをメインにする」ことと
「大会結果をPORTAL専用DBへコピーして別正本にする」ことを混同しない。

大会結果・記録は、
その情報を正式に管理する大会側の正本で更新し、
同じ本人識別を使ってPORTAL MY PAGEへ反映する。

運用上、開発者一人だけで全参加者の集計・確認・説明・訂正を担うことを前提にしない。

権限を持つ管理者が、
担当する大会・記録・運営情報を正規の管理経路から更新でき、
その正式更新が本人のPORTAL MY PAGEへつながる構造を目指す。

したがって完成系では、

- 開発者だけに更新作業を集中させない
- 管理者の正規更新経路を妨げない
- 参加者本人は自分のパーソナルデータと記録を継続して確認できる
- 管理者更新と本人データの紐付けで別人化しない
- 同じ記録をPORTAL用に二重保存しない
- 大会ごとに新しい本人プロフィールを作らない
- PORTAL導入時に既存登録者へ再登録を強制しない

ことを絶対条件とする。

今後のUI・認証・Firebase・駅伝・記録機能の判断で、
この核を局所的な実装都合によって壊してはいけない。

現在のPORTAL UI工程では、
まずこの完成系へつながる画面・導線を作る。

Firebase接続・既存登録者接続・管理者更新・記録反映については、
現行Auth / profileId / binding / event result正本を監査して成立確認後に接続する。

■ 0-H. 現在は「公開前」ではない【現実条件・固定】
==================================================

第一弾のEVENT BASEは、すでに公開済みである。

現時点で、

- 参加者へEVENT BASEのリンク配布済み
- 参加者登録が開始済み
- 既存の参加者・本人情報・大会binding・出走情報が存在する
- 利用者はすでに「大会のためのページ」としてEVENT BASEを使い始めている

という現実から開発を継続する。

したがって、TOP RUN PORTALを導入する際に、
「これから全員が初めてPORTALで登録する」
という公開前の前提へ戻してはいけない。

PORTALは、すでに稼働しているEVENT BASEの上に後から加える共通入口である。

PORTAL導入を理由に、

- 既存参加者へ名前の再登録を要求する
- 既存参加者へ新しい本人プロフィールを作らせる
- 既存EVENT BASE URLを突然無効化する
- 既存大会bindingを破棄してPORTAL用に作り直す
- 既存の出走登録を別データへ移し替える

ことを前提にしない。

既存登録者がPORTALを使い始める場合、
「すでに登録済みの同じ本人として継続できること」が成立条件である。

その接続方法は、現行Auth / profiles / profileId / binding / eventIdを監査してから確定する。
未確認の状態で「自動的に同じ本人として復元できる」と断定しない。


==================================================
■ 0-I. 既存EVENT BASEとPORTALは移行期間中に共存できる【固定】

TOP RUN PORTALを導入しても、ただちに既存EVENT BASEの直接URLを排除しない。

少なくとも移行・検証期間は、

        ＋
    TOP RUN PORTAL共通入口

が共存できる前提で設計する。

PORTALを利用しない参加者がいることを許容する。

PORTALを経由しないと大会が使えない構造へ、確認なく変更しない。

最終的に入口をPORTALへ集約するかどうかは、

- 実際の利用状況
- 重複登録の減少
- 操作の分かりやすさ
- 本人継続性
- 安定性
- ユーザー実機確認

を見て判断する。

「PORTALを作ったから全員を移す」ではない。


==================================================
■ 0-J. 総合プラットフォーム構想は「強制実装計画」ではない【固定】
==================================================

旅ランQUESTを起点にした総合プラットフォーム構想は保持する。

ただし、この構想は、

- すべての利用者が現在その全体像を理解している
- すべての機能に現在需要がある
- すべての機能を必ず実装する
- 開発を無期限に継続する

ことを意味しない。

利用者は、現時点で必要な機能だけを使えばよい。
総合構想を理解することを利用条件にしない。

ユーザー自身も、需要・利用状況・開発の安定性・継続可能性を見て、
将来の機能拡張を続けるか、止めるか、限定するかを判断できる。

したがって、ChatGPTは将来構想を理由に、
現在不要な巨大機能・新認証・新DB・複雑な移行処理を先回りして実装してはいけない。

現在必要な機能を成立させ、
将来増やせる余地だけを残す。

「拡張可能」と「今すぐ拡張する」を混同しない。

■ 0-K. 現在の参加者から見える世界と内部構想を混同しない【固定】
==================================================

現在の参加者の多くは、TOP RUN全体の将来構想を前提に利用しているわけではない。

参加者から見える現状は、主に、

    配布された大会リンク
        ↓

        ↓

        ↓

である。

「この大会へ入るための登録」
と理解することは自然である。

ChatGPTは、既存登録を後から勝手に
「PORTAL全体への登録だった」
「総合プラットフォーム会員登録だった」
と再定義してはいけない。

将来PORTALへ接続するときは、
技術的な共通本人基盤を活用しながらも、
利用者に必要な意味・操作だけを分かりやすく見せる。

Firebase Auth、profileId、binding等の内部概念を利用者へ理解させることを前提にしない。


==================================================
■ 0-L. 認証の将来イメージと現在の事実を分離する【重要】
==================================================

将来イメージとして、

    ホーム画面等のTOP RUN PORTALアイコン
        ↓
    PORTALを開く
        ↓
    必要な初回認証
        ↓
    以後PORTAL内でMY PAGE / CALENDAR / EVENTS等へ移動

というアプリ風の共通入口を目指す余地を持つ。

ただし、これは完成形の方向であり、
現在すでに登録済みの参加者へ新しい初回登録をやり直させる意味ではない。

また、現行の匿名Authを使用している範囲では、
別端末・別ブラウザ・データ消去後まで同一人物として復旧できるかは別問題である。

PORTAL完成時の認証方式を確定する前に、

- 既存参加者が何で本人として成立しているか
- 同一ブラウザでどこまで復帰できるか
- 別ブラウザ／別端末で何が変わるか

■ 0-Q. 通知機能ロードマップ【Android / iPhone / iPad / PC共通・重要】

- Android：
  対応ブラウザ／PWAでWeb Pushを利用できる構造を目指す。
- iPhone / iPad：
  Home Screen Web AppでのWeb Pushを前提にする。
- PC：
  対応ブラウザでは同じWeb Push思想で利用できる余地を持つ。
- OS名や端末名だけで処理を固定せず、

    PORTALを開く
        ↓
    必要に応じてホーム画面追加／PWAインストール案内
        ↓

        ↓

        ↓
    購読登録
        ↓
    PORTALから通知受信

とする方向を検討する。

通知許可は、
画面表示直後に突然要求せず、
ユーザー操作を起点とする。

想定通知：

- PORTALのお知らせ
- 大会情報の更新
- 練習予定の追加／変更

利用者が必要なものを選択できる方向とする。

「PORTAL内のお知らせ表示」と
「OSへ届くPush通知」は別機能として分離する。

PORTAL内お知らせ：
    画面を開いた時に確認する情報

Push通知：
    PORTALを開いていなくても届ける必要がある情報

とする。

■ 0-S3. 運用コスト方針：無料運用を前提とする【固定】

EVENT BASE / TOP RUN PORTALのインフラ運用は、

    無料運用を前提とする。

これを固定方針とする。

ただし「無料プランに留まり続けること」自体を目的にしない。
現在規模で無料枠に収まる構成を優先し、
利用者・団体・通信量・保存量・通知量等が拡大して無料枠では現実的に成立しなくなった場合は、
必要性・費用・代替案を確認した上で有料化を許容する。

ユーザーの運用方針：

    現在：概ね50人
    来年度：概ね100人

    無料が前提。
    現在規模で不要な費用はかけない。
    規模が拡大し、有料化が合理的・必要になった場合はやむなし。
    ただしユーザーが把握・判断しないまま有料化しない。

Cloud Run等、利用開始のためにCloud Billingアカウントの紐付けを要求するサービスでは、

    課金を有効にすること

    実際に有料利用が発生すること

を混同しない。

したがって、Blaze移行後は「上限超過時に停止するSpark」とは違い、
利用量・Billing・予算通知を監視する運用を前提とする。

本人引継ぎ方式を本番採用する場合、
Cloud Runまたは同等の信頼されたサーバー処理は本番でも継続して必要である。
実証だけの一時設備とは扱わない。

料金体系・無料枠・請求条件は変更される可能性があるため、
以下の数値は「2026-10-03に公式料金を再確認した費用設計基準」とする。
恒久的な固定料金表とは扱わず、

--------------------------------------------------
A. Firebase Realtime Database
--------------------------------------------------

2026-10-03公式条件：
- Blazeでも保存 1 GBまでは無料使用量
- Blazeでもダウンロード 10 GB/月までは無料使用量
- 超過ダウンロードは $1 / GB
- Blazeの同時接続上限は1データベースあたり200,000
- Sparkの同時接続上限は100

Cloud Runを使うためevent-base-rebuildをBlazeへ移行した後は、
100人規模で「同時接続100」というSpark上限そのものは主要制約ではなくなる。
一方、ダウンロード10 GB/月は引き続き重要な無料枠である。

31日/月で10 GBを人数だけで均等割りした「無料枠の目安」は、

50人：
    約200 MB / 人・月
    約6.45 MB / 人・日

100人：
    約100 MB / 人・月
    約3.23 MB / 人・日

これは実際の割当ではなく、無料枠を人数で割った監視目安である。

通信量モデル：

平均 1 MB / 人・日 の場合
    50人  = 約1.55 GB/月
    100人 = 約3.10 GB/月

平均 2 MB / 人・日 の場合
    50人  = 約3.10 GB/月
    100人 = 約6.20 GB/月

平均 3 MB / 人・日 の場合
    50人  = 約4.65 GB/月
    100人 = 約9.30 GB/月

平均 4 MB / 人・日 の場合
    50人  = 約6.20 GB/月
    100人 = 約12.40 GB/月

100人で平均4 MB / 人・日まで増えると、
10 GB無料枠を約2.4 GB超える計算となり、
ダウンロード超過分だけなら概算 $2.40 / 月となる。
実請求にはプロトコル・暗号化等の通信オーバーヘッドも含まれるため、
この$2.40を上限額とは扱わない。

重要：
現行EVENT_BASE_PRODUCTION.htmlでは、
新Firebase coreが events/<eventId> に対して onValue(rootRef()) を使用していることをコード確認済み。
Firebase公式も、onValueは指定位置の子を含む変更ごとに発火し、
スナップショットを大きくしないため必要な最小レベルへlistenerを置くよう案内している。

したがって、100人運用で無料枠を守るうえでは、
LIVE / CHAT / 位置共有など高頻度更新を含む実使用時の「Downloads」を実測することが重要である。
ただし、費用対策を理由に現在のCanonical Event Stateや接続設計を勝手に変更してはいけない。
必要になった場合は、現行挙動・Rules・同期への影響を監査した独立TARGETとして扱う。

内部監視基準：
- 月7 GB到達：無料枠70%として原因・増加傾向を確認
- 月9 GB到達：無料枠90%として通信増加を伴う追加実装を一旦見直す
- 月10 GB超過見込み：有料化を許容するか、構造改善するかをユーザー判断前に比較する


--------------------------------------------------
B. Cloud Run 本人引継ぎサーバー
--------------------------------------------------

2026-10-03公式無料枠（リクエストベース課金）：
- 2,000,000 requests / 月
- 180,000 vCPU-seconds / 月
- 360,000 GiB-seconds RAM / 月

本人引継ぎサーバーは全通常通信を中継するサーバーではなく、
主にワンタイムコードとFirebase Custom Token発行に使用する。

余裕を見るためのストレス試算：

仮定：
- 1人が月10回本人引継ぎを行う
- 1回の引継ぎでCloud Runへ4リクエスト
- 各リクエストが1 vCPUを1秒使用
- メモリ512 MiBを1秒使用

50人：
    2,000 requests / 月       = 無料枠の0.10%
    2,000 vCPU-seconds / 月   = 無料枠の約1.11%
    1,000 GiB-seconds / 月    = 無料枠の約0.28%

100人：
    4,000 requests / 月       = 無料枠の0.20%
    4,000 vCPU-seconds / 月   = 無料枠の約2.22%
    2,000 GiB-seconds / 月    = 無料枠の約0.56%

この仮定は通常想定より多めの本人引継ぎ回数を置いた費用確認用モデルであり、
100人規模でもCloud Run無料枠に対して大きな余裕がある。

Cloud Runの費用抑制条件：
- リクエストベース課金を基本とする
- minimum instances = 0 を基本とする
- 常時稼働が必要と確認されるまでminimum instancesを増やさない
- 本人引継ぎ以外の常時処理を無断でCloud Runへ載せない

Google公式では、リクエストベース課金かつminimum instances=0の場合、
アイドル時のインスタンス料金は発生しない。


--------------------------------------------------
C. Cloud Build / Artifact Registry / Cloud Logging
--------------------------------------------------

Cloud Build：
2026-10-03公式では、請求先アカウントあたり月2,500 build-minutesの無料枠がある。

費用確認モデル：
    月20回デプロイ × 1回5分 = 100 build-minutes / 月
    → 無料枠の4%

実際のデプロイ回数・ビルド時間は未計測のため、これは計画上の仮定である。

Artifact Registry：
    0.5 GiB-monthまで無料。

利用者50人 / 100人という人数より、
デプロイ履歴・古いコンテナイメージの蓄積が費用要因になる。
実配置後に実イメージ容量を確認し、不要な旧イメージを無制限に残さない。

Cloud Logging：
    公式無料枠は最初の50 GiB / project / month。
本人引継ぎ用途100人規模では通常の主要コスト要因とは考えにくいが、
個人情報・トークン・ワンタイムコードをログへ出さないことを費用以前の安全条件とする。


--------------------------------------------------
D. GitHub Pages
--------------------------------------------------

GitHub Pages公式の主な目安：
- 公開サイト 1 GB以下
- source repository 推奨 1 GB以下
- soft bandwidth limit 100 GB / 月

実ページ総転送量は、背景画像等を含む最終公開アセットでまだ実測していない。
そこで費用・容量確認用に、

    1回のフル読み込み = 5 MB
    1人 1日2回読み込み
    31日/月

という保守的なモデルを置く。

50人：
    5 MB × 2回 × 31日 × 50人
    = 約15.5 GB / 月
    = soft bandwidth limitの15.5%

100人：
    5 MB × 2回 × 31日 × 100人
    = 約31 GB / 月
    = soft bandwidth limitの31%

したがって、100人規模でもこのモデルでは十分な余裕がある。
ブラウザキャッシュ等が効けば実転送量はさらに下がる可能性がある。
一方、巨大画像・動画をGitHub Pagesへ追加する場合は別途再計算する。


--------------------------------------------------
E. Firebase Authentication
--------------------------------------------------

現行本人基盤はFirebase Anonymous Authを使用し、
本人引継ぎ実証ではCustom Tokenで同じUIDへ接続する方針である。

現在使用していないPhone Auth / SMS認証を勝手に追加しない。
100人規模で現在のAnonymous Auth / Custom Token本人引継ぎを使うこと自体を、
主要な有料化要因とは扱わない。


--------------------------------------------------
F. 50人 → 100人の費用判断
--------------------------------------------------

現在50人：
- Cloud Run本人引継ぎ：無料枠に対して十分な余裕
- GitHub Pages：保守的モデルでも約15.5 GB/月、soft limit 100 GB/月に余裕
- Firebase RTDB：平均4 MB/人・日でも約6.2 GB/月で10 GB無料枠内
- 月額0円を基本目標として進める

来年度100人：
- Cloud Run本人引継ぎ：無料枠に対して十分な余裕
- GitHub Pages：保守的モデルでも約31 GB/月、soft limit 100 GB/月に余裕
- Firebase RTDB：平均2 MB/人・日なら約6.2 GB/月
- Firebase RTDB：平均3 MB/人・日なら約9.3 GB/月で無料枠に近づく
- Firebase RTDB：平均4 MB/人・日なら約12.4 GB/月で無料枠超過

よって、100人までは「有料化前提」ではなく、
引き続き月額0円を狙う設計でよい。
ただし100人運用ではFirebase Downloadsを重点監視し、
実測が月7 GBを超え始めた時点で早めに再評価する。

100人を超える見込み、複数団体運用開始、Web Push大量配信、
LIVE / CHAT / 位置共有の利用頻度増加、画像・PDF等の大容量データ増加、
Cloud Runの役割拡張が発生した場合は、
その時点の公式料金と実測値で再計算する。

「無料を守るために機能を壊す」ことも、
「便利だから先に有料化する」ことも行わない。
実利用・費用・必要性を確認してユーザーが判断する。

A. 第一回実運用で確認された事実【ユーザー実運用報告】

- 第一回実運用では二重登録が非常に多かった。
- これは既存MASTERですでに確認していた、別ブラウザ・別端末・入口迷いによる再登録問題が、実運用でも重要課題になったことを意味する。

- 既存profiles / profileId / binding / players / timingRecordsを確認せず削除・統合しない。

今後のTARGET：
- 新規登録前に「すでに登録済みではないか」を確認できる導線。
- 既存本人を選んで継続できる導線。
- 同一人物の重複候補を開発者／管理者が確認できる保守機能。
- 誤統合を防ぐため、自動統合ではなく確認を伴う方式。
- PORTAL共通入口と本人引継ぎを利用して、別ブラウザ・別端末で別人化しにくい構造へつなぐ。


3. 中学生・保護者端末の実運用

第一回実運用で、以下の現実ケースが発生した。

- 中学生本人がスマートフォンを持っていない。
- 親のスマートフォンで参加登録・操作する。
- 親が登録操作を行い、表示名には子どもの名前を使用する。
- 親自身の利用と、子どもの大会参加を同じ端末から扱う可能性がある。
- 「Firebase Auth UID = 競技者本人」と単純に扱えないケースが現実に存在する。

このケースでは、

    操作している人／端末
        と
    大会に出場する競技者本人

を同一概念にしてはいけない。

ただし、この実運用事実を理由に、

- 新しい本人ID
- 保護者専用の別人物DB
- 駅伝専用プロフィール
- 新profileId体系
- 新binding体系

を確認なしに追加しない。

現行の players に存在する ownerUid / subjectUid / profileId、
profiles/<uid>、bindings/<eventId>/<uid>、
COMMON PROFILE / PLAYER CARDの関係を実データで監査してから、
「誰が操作するか」と「誰の競技記録か」を安全に分離する方法を決める。


4. 親端末から本人端末への引継ぎが必要

中学生本人が後からスマートフォンを持つ場合、または別端末へ移行する場合に、
既存の出走・記録・PLAYER CARD・COMMON PROFILEを失わず引き継げる必要がある。

また、

- 親が子どもの表示名で登録済み
- 親自身も別の参加者として利用する
- 兄弟姉妹を同じ親端末で扱う

等の将来ケースでも、別人混同を起こさない構造が必要である。

この引継ぎは、MASTER既存の

    既存UID
        ↓
    一時引継ぎコード
        ↓
    信頼されたサーバー
        ↓
    Firebase Custom Token
        ↓
    同じUID / profileId

という「端末間本人引継ぎ」と同一問題とは限らない。

今回新たに、

    端末／操作者の引継ぎ
        と
    競技者本人の所属・所有関係の引継ぎ

を分けて考える必要がある。

現時点ではFirebase pathや具体的所有モデルを確定しない。
既存実データ監査後に独立TARGETとして設計する。


--------------------------------------------------
B. 過去の同期・Firebase不具合を引き続き再発防止対象とする
--------------------------------------------------

第一回実運用後の修正でも、過去に繰り返した以下を忘れない。

- 保存できたように見えて、再読込すると前の状態へ戻る。
- 片側では更新され、別端末には即時反映されない。
- 保存・読込・認証・binding・共有を局所修正した結果、別機能が退行する。
- localStorage / Firebase / 初期値等の正本が競合し、古い状態が再上書きされる。
- localStorage容量枯渇や保存失敗を成功扱いしたことがある。
- タブクリア／再起動／PORTAL導入周辺で、bindingや本人復帰が不安定化した履歴がある。
- CHATで送信・ACK・タイムアウトの不具合履歴がある。

34-C. LIVE開始問題：2026-10-05コード確認済み事実
--------------------------------------------------

対象：
    EVENT_BASE_PRODUCTION.html
    EVENT_BASE_v81.html

v81のLIVE開始主要経路は、現行本番と同一であることをコード比較で確認した。

確認した経路：

    acquireLiveStartPosition168
        ↓
    startLiveShare
        ↓
    EventBaseLiveV45.start
        ↓
    EventBaseConnectionAPI.setLive
        ↓
    events/<eventId>/live/<uid>

確認済み：

1. LIVE開始時、GPS精度が60m以下になることを必須条件としている。
2. v81までは acquireLiveStartPosition168(60,16000) を使用し、
   16秒以内に60m以下へ到達しなければ開始失敗となる。
3. 位置情報権限拒否（geolocation error code=1）は即時失敗となる。
4. その他の一時的なGPSエラーは即時失敗させず、外側の待機時間まで待つ。
5. 会場距離判定はGPS取得後、Firebase初回write前に行う。
6. safety / event complete / emergency stop等の安全判定が別に存在する。
7. Firebase初回writeは EventBaseLiveV45.start 内の setLive で行われる。
8. setLive前にbinding/session確認が存在する。
9. LIVE開始失敗は、位置情報権限だけでなく、GPS精度・会場距離・safety・binding・Rules/networkのいずれでも起こり得る。
10. 「60m／16秒」はコード上の確実な開始阻害要因の一つだが、第一回本番での唯一の原因とは確定していない。

追加コード事実：

- acquireLiveStartPosition168 の timeout時、bestAccuracy が null の場合でも
  Number(null) が 0 となる判定経路があり、
  エラー表示が「最良 約0m」のように誤分類される可能性がある。
- acceptLiveGpsFix158 は60m超を送信しない意図の関数として残っているが、
  現在の EventBaseLiveV45 の継続送信経路で直接使われていないため、
  初回開始精度と継続送信精度の扱いは今後改めて監査対象とする。

- 取消操作が別端末へ反映される

--------------------------------------------------

襷渡しは駅伝の中核機能として維持する。

CATCH → RELEASE は別の意味を持つ操作として保持する。
開発者限定運用にしたことを理由に、
CATCH / RELEASEを勝手に単一操作へ統合しない。

STARTは予定時刻による自動開始にしない。
開発者のSTART操作によって実開始時刻を記録する。

手動計測値は速報・運用値として扱い、
大会公式記録そのものと混同しない。

■ 36. 実機検証の入口URLと役割表示・往復確認【2026-10-09追記／固定】
==================================================

【追記の理由・ユーザー実機報告】
2026-10-09のTOP RUN PORTALの実機検証で、ユーザーが「管理者アイコンがない」
「MY PAGEを開いて戻った後に管理アイコンが消える」と報告した。
ChatGPT側の模擬ブラウザ検査結果とユーザーのiPhone実機結果が一致していない。
この不一致を未解決のまま「検証済み」「修正済み」と扱ってはならない。
入口のリンク先を一種類だけ提示する、または間違った版・役割のURLを提示することは、
実機検証そのものを成立不能にする納品品質上の重大な問題である。

【実機検証の目的】
ユーザーは単に画面を見るのではなく、開発者・参加者のページを比較し、
表示項目、操作導線、MY PAGE、保存状態、再入場、管理画面入口などを検証している。
ChatGPTは実機検証の入口を正確に準備しなければならない。

【2役割以上の実機比較時のURL提示形式・固定】
1. 開発者用URLと参加者用URLを、同じ回答の中に必ず2本並べて表示する。
   両方を役割名「開発者」「参加者」で明確に区別し、タップできる形式で提示する。
   iPhoneからURLをコピーできるよう、必要ならプレーンテキストでも提示する。
2. 両方とも今回納品する同じHTMLファイルを指し、役割を指定するクエリのみ区別する。
   開発者用の確認URLには ?role=developer、参加者用には ?role=participant を用いる
   （当該HTMLの実コードで役割判定を確認すること。将来実装が変わればコードに従う）。
3. 古いファイル名、以前の未承認候補、別のイベントURLを混ぜてはならない。
4. 第30節の「確認用GitHub Pages URL 1本」は単一画面の通常納品に適用する。
   ユーザーが複数の役割入口を求めた実機比較では、この第36節を優先して必要数を提示する。
   HTMLファイルのダウンロードリンク自体は1本でよい。
5. GitHubアップロード前は「アップロード後の確認用URL」と明記し、
   実際にアップロードしたか、公開URLを読み込めたか、iPhoneで動いたかを混同しない。

【リンク先と入口表示の事前検査・必須】
1. まず最新MASTER全文、承認済み基準HTML、今回の納品HTML、直近退行履歴を確認する。
2. 納品するHTMLの実ファイル名とURLのファイル名が完全一致するか確認する。
3. 実HTMLの role / ownerKey / 権限表示条件を読み、
   開発者入口と参加者入口のパラメータがそれぞれ正しいか確認する。
4. ChatGPT側のブラウザで両方の条件を起動し、少なくとも次を確認する。
   - 開発者入口：開発者向け表示、HOMEの管理画面アイコン／入口が見える。
   - 参加者入口：参加者向け表示、管理者専用入口が見えない。
   - 開発者入口：MY PAGE → HOMEに戻る後にも管理画面アイコンが表示される。
   - 開発者入口：管理画面へ入れる。参加者側に管理画面が露出していない。
   - 開発者の参加者確認モード：選択・復帰後も本来の開発者権限と入口が保持される。
5. アイコンのCSS表示状態だけでなく、位置・重なり・タップ可否を確認する。
   少なくともユーザーのiPhoneに近い画面幅で検査する。
6. ローカルHTMLでのブラウザ検査、GitHub Pagesでの確認、ユーザーiPhone実機確認を
   個別に記録し、異なる検査結果を同じ「確認済み」にまとめない。
7. リンク先の公開状態を確認できない場合は正直に「未確認」と記す。
   404や別版の混在が確認された場合、実機検証用として案内せず原因を解消する。

【異常時の停止条件】
- 開発者URLで参加者画面が開く、管理画面アイコンが消える、
  管理画面へ入れない、または再読込・MY PAGE往復で役割表示が変わる場合、
  そのHTMLを「実機検証準備OK」「修正済み」として案内しない。
- 実機では消えたがローカルブラウザでは再現しない場合、原因は未確定。
  実機報告を否定せず、公開URL・端末表示・役割状態の食い違いを優先調査する。
- 未確認の修正を重ねたり、管理アイコンを強制表示するだけで問題を隠さない。
- 参加者確認モードは開発者本人の認証・profileId・bindingを変更せず、
  あくまで開発者専用の表示確認機能とする。Firebase未接続のローカル確認対象を
  実参加者・実保存状態と呼んではならない。

- 新大会用localStorage／当日計測cacheは新ID別に分離し、旧大会IDを直接指定したFirebase書込コードは検出していない。旧IDはコメントおよび大会固有予定タイマー条件に残るが、書込先ではない。
